# ArchReason 引擎 · 参考图合规使用与产出独立性设计

> 日期：2026-10-09
> 前提：开发期需要用案例图辅助设计判断，但**最终产出中不输出任何受版权保护的图片**
> 目标：把这条界线做成工程上真实存在、可审计的隔离，而不是靠自觉

## 一、设计前提：参考与产出是两个不相交的集合

版权保护的是**具体表达**（一张照片的像素、构图、光影），不保护**思想、方法、风格与功能**（空间组织方式、设计策略、比例关系、色彩倾向）。这就是"思想—表达二分法"。

由此得到一个可直接工程化的结论：

- 从案例图里**提取抽象特征**（色板数值、构图比例、明度分布）—— 得到的是"思想/方法"层面的信息；
- **复制其像素**（热链、缓存、嵌入产出）—— 才是"表达"层面的使用。

所以本方案的全部设计，就是把这条界线落到一条**真实的数据边界**上：参考图永远停在 L0，只有**数值参数**能穿过去。

## 二、架构设计：五层两集合

```
┌─ 参考集合（dev-only，不进产物）──────────────┐
│  L0  参考层：案例图库 / 人工核验 / 视觉调参    │
└──────────────── 合规边界 ← 只有数值参数可跨越 ──┘
┌─ 产出集合（runtime，可独立交付）─────────────┐
│  L1  抽象层：特征提取 → 数值参数              │
│  L2  推理层：策略池 · 概念推理 · 协同关系      │
│  L3  生成层：本地 SVG / 文生图（素材自产）     │
│  L4  交付层：报告 · 概念图 · 方案文本          │
└──────────────────────────────────────────────┘
```

**边界的三种落地形式**（缺一不可）：

| 形式 | 做什么 | 对应文件 |
|---|---|---|
| 构建排除 | 参考图与 profile 不进 `dist` | `vite.config.ts`、`.gitignore` |
| 数据隔离 | 生产环境不挂载参考图代理路由 | `server/routes/gooood.ts` |
| 出口审计 | 产出物做 pHash 比对 + 路径引用检查 | `scripts/audit-output.mjs` |

## 三、核心功能模块

### 1. 参考图管理（L0，dev-only）
- **入库**：下载 → 剥 EXIF/XMP → 统一尺寸 → 存 `data/reference/`（gitignore）
- **来源台账**：每条记录 `sourceUrl / author / license / fetchedAt / purpose`，落 `data/reference/ledger.json`
- **用途白名单**：仅"人工核验、视觉调参"，不参与任何运行时请求

### 2. 特征提取（L1）
输出 `ReferenceProfile`，**纯数值，不可逆**（从参数无法还原原图）：

```ts
interface ReferenceProfile {
  caseId: string;
  palette: { hex: string; ratio: number }[];  // k-means 主色
  luminance: number[];                        // 明度直方图（16 桶）
  aspect: number;                             // 画面长宽比
  composition: 'centered' | 'thirds' | 'symmetric' | 'panoramic';
  materialTendency?: string[];                // 人工标注，如 ['清水混凝土','青砖']
}
```

关键约束：**该结构里不存在任何可还原原图的字段**（无 URL、无缩略图、无感知哈希原值）。

### 3. 策略推理（L2）
- 复用现有 42 条策略池与协同关系
- 输入：用户需求文本 + `ReferenceProfile`（仅数值）
- 输出：策略组合 + 设计参数向量（如"主色偏暖灰、体量横向展开、绿化覆盖率高"）

### 4. 生成（L3）
- **本地 SVG 程序化概念图**：复用 `imageGeneration.ts` 现有的 8 风格，纯代码绘制，天然无外部像素
- **文生图**：prompt 由策略与参数拼装，**绝不把参考图作为输入**
- **明确禁止 `img2img` / 垫图**：这是最容易越界的一步——垫图会把参考图的表达直接带进产出

### 5. 合规审计（出口）
- **pHash 比对**：产出图与参考图库做感知哈希距离比对，低于阈值即拦下人工复核
- **EXIF 检查**：产出图必须无可溯源元数据
- **引用检查**：产出物中不得出现 `data/reference/` 或上游图片 URL

## 四、图像处理流程（六步）

1. **参考图**（L0）：案例库原图，仅本地可见
2. **归一化**：剥 EXIF、统一尺寸，避免元数据泄露来源
3. **特征提取**：色板 / 明度 / 构图比例 → 纯数值
4. **参数化**：写入 `ReferenceProfile`，**参考图像素到此为止**
5. **生成**：以参数为条件，由引擎自产 SVG 或文生图
6. **校验 → 交付**：pHash 相似度比对通过后，产出物进入报告与概念图

## 五、四条硬约束（建议写进 AGENTS.md）

1. **只读不复制** —— 参考图只读；不写进 `dist`、不写进云存储、不出现在任何 API 响应里
2. **只抽象不搬运** —— 跨越边界的只能是数值；任何"把图当作参数传进去"的实现都算越界
3. **单向数据流** —— 产出物永不回指参考图；不做"产出图 → 反向匹配参考图"的回链
4. **台账可审计** —— 每张参考图的来源、许可、用途可查；产出物记录的是"用了哪条策略、哪些参数"，不是"用了哪张图"

## 七、边界与风险提示

- **pHash 是技术兜底，不是法律判断**。"是否构成实质性相似"最终仍需人工判断，pHash 只能拦住像素级近似。
- **警惕"自己画的也像"**。若产出图是某个知名建筑的正面复刻（即便全自绘），风险依然存在 —— 所以产出应停在**概念/示意**层级，不追求复刻具体作品。
- **风格学习与表达复制之间没有自动分界线**。本方案的假设是：只要产出是"参数驱动的重新生成"而非"素材搬运"，就落在思想/方法一侧；这个假设需要你在对外发布前做一次法律确认。
- **参考图台账是自证清白的唯一凭据**。一旦发生质疑，"每张图从哪来、怎么用、有没有进产出"的完整记录，比任何技术手段都有效。
